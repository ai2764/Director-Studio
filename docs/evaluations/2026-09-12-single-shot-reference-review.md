# 单镜头 reference 变更后的逐图重审

## 范围与入口

仅处理用户修改的那一个镜头的当前全部 Picture refs，不扫描其他镜头。
现有 Director 界面保存 Edit materials 后会发送 `materialReviewMessage`；
reference 增删/换序会设置 `material_review_pending`。Agent 调用该镜头的
`write_prompt` 时，由 Python 执行完整审图，不依赖最多四张的普通聊天附件。
可选的 materials API `rewrite_prompt=true` 也走同一服务。

本轮没有增加后台 Agent、自动生成媒体、Node 状态库或新的 Harness 循环。
legacy 与 Harness 共享这条后端业务链路。

## 处理契约

1. 固定 1–9 张当前 refs 的顺序、角色、素材、实际文件键、文件名、内容 SHA256
   及批准的说明。显式文件缺失时禁止用同素材的另一张图替代。
2. 对待重审镜头逐张读取全部 refs，每次一张最长边 768 像素的 JPEG；
   使用现有视觉 provider 和显存租约。要求完整的结构化可读性、观察及疑点结果。
3. 汇总观察、原 Creative brief（现有 `script_beat`）、剧本、对话、时长和原提示词，
   决定保留或修改。不得因图片随意改剧情；有需要用户选择的冲突则停止并返回问题。
4. 必要时生成六段 H3 提示词；校验全部当前 Picture 绑定、Audio 绑定、对话及
   非空段落。模型要求保留的旧提示词若不满足绑定/结构要求，仍须重写。
5. 保存前重读镜头/剧本及图片内容指纹；变化则拒绝保存旧版本结果。brief、prompt
   和完成的审图证据一并保存，最后才清除待重审。邻镜和项目剧本不变。

已完成审图可以在 refs 内容/说明未变、没有新的待重审标记时复用；一旦 reference
变更，重审整个当前集合，不只补看新图。同 ID 覆盖文件不能复用旧证据。
重校验之前先关闭完成状态，因此文件丢失、模型失败或提示词阶段图片变化也会保留
待重审状态；旧 brief/prompt 不被失败尝试覆盖。失败会通过工具明确返回 `ok: false`，
不追加成功动作。没有增加自动无限重试。

实际 brief 改变时，旧 H3 job 链接归档并解除，镜头恢复待审。正在排队/运行的 H3
任务（含实际 job 状态）会阻止这条重审写入流程，不取消用户任务。文件存储仍是
现有单后端的乐观检查，不宣称跨进程数据库事务或解决全部历史任务同步问题。
