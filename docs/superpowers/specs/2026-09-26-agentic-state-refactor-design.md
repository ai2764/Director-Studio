# DS Agentic System：任务上下文与状态边界重构计划

日期：2026-09-26

代码基线：`ecfee97`，分支 `feature/mv-mode`。

状态：供用户审阅的架构设计与迁移路线，尚未授权实现；不是逐文件执行清单。

## 1. 目标和共同理解

目标不是给导演 Agent 写一张覆盖所有创作情况的大状态转换表，而是让它看到正确事实、执行可靠操作、收到真实反馈，并在失败后自主采取有效的下一步。

用户原则：降低框架错误率，保留 LLM 创作自由；避免角色、服装、场景、措辞等业务关键词硬编码；修系统而非手动修某部影片；用传统软件工程可理解的方式解释取舍。

本设计采用的前提：保留现有项目、媒体和外部生成能力；本机单后端为主；渐进迁移。多用户协作、分布式调度和云部署不作为这一轮的设计前提。

成功不是“报错文字更少”，而是陈旧输入误用、重复提交、错误覆盖、无效重试和用户救场减少，同时不增加对合理创作变体的误拦。

新增的共同方向：上层按 Agent 正在做的任务组织能力和上下文，底层按事实与执行职责解耦。任务划分不等于多个独立 Agent，也不等于固定工作流。模型可以按需查询、扩大观察范围、切换任务；这些行为不能扩大原有修改和执行权限。

### 一分钟路线

1. 先测清楚：当前模型到底看见哪些信息，错误出在信息缺失、旧信息干扰、决策还是执行。
2. 先试一个任务：单 Shot 提示词工作包，保留完整必要证据与查询入口，和现有上下文做对照。
3. 再统一修改：UI、聊天和托管对同一个 Shot 使用同一套修改、失效和结果激活规则。
4. 再做可靠续跑：持久化操作回执，分清等待、失败、取消，尾帧绑定确切视频版本。
5. 最后推广和清理：扩展其他任务工作包，前端使用统一状态视图，删除重复逻辑。

第一批可实施范围建议仅为 P0/P1A：测量基线和提示词任务上下文试点，不先换数据库、不同时重写整套状态管理。

## 3. 方案选择

| 方案 | 优点 | 主要问题 |
| --- | --- | --- |
| 整理现有状态枚举、继续局部补丁 | 迁移成本最低 | 事实仍有多个写入者，失效和恢复规则容易再次分叉 |
| 模块化业务内核 + 明确依赖 + 可靠操作协议 | 可渐进落地，能单独测试决策与执行，保留现有运行时 | 需要认真迁移写入口和兼容投影 |
| 全面重写或引入重型工作流平台、多 Agent 分工 | 可能适合更大规模运行 | 并不自动解决业务状态混乱，当前增加不必要的迁移面 |

推荐第二种，并加入任务工作包。模块化是实现手段；模型获得最小但充分的任务上下文、系统保持唯一事实来源和可靠执行，才是核心。只裁剪 prompt 容易漏信息；直接分多个 Agent 会新增交接与事实同步问题，所以先采用单 Agent、多任务工作包。

## 4. 目标职责边界

### 4.1 决策与可靠执行分离

LLM 决定镜头语言、表演、参考组合、哪些镜头衔接、如何修复、下一步做什么。它可以修改计划，不必走固定的“剧本—参考图—提示词—视频”流水线。

框架负责对象身份、版本、权限、作用范围、提交回执、资源租约和执行事实。LLM 提交业务命令，不直接写生命周期状态或给自己扩大权限。

通用循环是“观察—决策—行动—反馈”。这是交互协议，不是规定创作动作顺序的业务状态机。

### 4.2 四类领域对象

| 对象 | 权威内容 | 不负责什么 |
| --- | --- | --- |
| `ShotSpec` | 当前创作要求、逐句对白、镜头要求、参考选择和版本 | 不表示 Job 是否运行，不保存唯一的全局成功状态 |
| `Artifact` | 提示词、参考图、视频、尾帧等产物及其输入来源 | 存在不等于已选中，也不等于匹配当前规格 |
| `Operation` | 一次逻辑操作的身份、输入快照、尝试、回执、执行结果 | 不自行判断艺术质量，不替用户扩大范围 |
| `ManagedRun` | 授权目标、选中范围、当前计划、操作关联、等待原因、预算 | 不复制底层 Job 状态，不成为另一份 Shot 真相 |

这些是逻辑边界，不要求第一步物理拆成四个数据库。现有 `JobRecord` 继续承担生成执行记录；Operation 与 Job 的关系是“一次逻辑请求及其明确关联的执行尝试”，不再造两个互相同步的生成状态机。

产物内容和输入清单不可原地改写。选择关系可更新：一个目标 Shot 的当前衔接输入只能指向一个尾帧版本；历史尾帧不删除。这个限制不意味着所有角色、场景或 Layout 引用只能选一张。

### 4.3 结构化视图取代万能 Shot.status

后端提供 `ShotView`：规格版本、提示词有效性、当前选择的视频、运行中的操作、阻塞原因、可用动作和历史结果摘要。界面可以同时呈现“旧视频可看”“新版提示词需更新”“新任务等待 GPU”。

准备状态至少区分 `ready / stale / missing / unresolved`，并附依赖差异。它是计算结果，不由 UI、Agent、Job callback 各写一遍。

迁移期旧 `status` 仍作为兼容输出；旧入口输入不能直接决定新内核状态。兼容转换集中在一个地方，不能让前端和 Agent 各做一套优先级推断。

### 4.4 按 Agent 的实际任务组织工作包

工作包是同一决策 Agent 的不同视野，不是独立拥有状态的“角色 Agent”。任务可以来回切换，也可以分解；不是必须依次经过的阶段。

| 任务 | 默认载入 | 默认不载入，但可查询 | 完成时返回 |
| --- | --- | --- | --- |
| 理解目标与推进计划 | 当前请求、项目目标、有效要求、镜头/产物/活动操作摘要 | 所有镜头全文、媒体、历史日志 | 下一步建议或合法命令，附目标与依据 |
| 剧本与分镜规划 | 相关剧本、人物关系、叙事要求、已有分镜概要 | Job 轮询记录、失败提示词全文 | 有来源的创作修改提案 |
| 素材与连续性处理 | 目标镜头要求、当前选中 ref、相关资产证据、实际依赖的前后镜头 | 全库图片、无关角色、旧生成详情 | 素材选择/生成/衔接提案及理由 |
| 单镜头提示词编写 | 当前 Shot 规格、逐句对白及来源、选中图像/音频、必要连续性、适用指南 | 全部聊天、其他镜头的完整提示词、历史失败日志 | 候选提示词、结构化绑定、必要的修改提案或缺失信息 |
| 结果评估 | 指定产物、该次生成输入、适用要求、待检查的问题 | 整个创作聊天过程 | 带证据的观察/问题/建议，不自动升级成用户要求 |
| 失败恢复与续跑 | 原操作输入、实际回执、错误分类、输入差异、已尝试方法、剩余预算 | 无关创作讨论和其他 run 的详细记录 | 查询/修复/重试/等待/询问的选择 |

“结果评估”工作包只组织已有评估能力，不在本重构中新增通用成片 QC 或自动重拍产品功能。Job 轮询、保存回执等确定性操作由执行层完成，不为每个机械步骤额外调用 LLM。

### 4.5 工作包契约：公共底座、任务材料、按需查询

每个工作包由后端基于权威事实构建，包括：

- `task_kind / target_ids / objective`：本次任务和目标，不用角色名或关键词判断业务规则。
- `authority`：真实会话授权范围、锁定项、允许的修改和预算；由后端核验，不接受模型自授权限。
- `source_versions`：任务实际使用对象的版本/内容签名，保留 stale 检查。
- `requirements`：当前适用的明确要求和来源；最新用户请求保留原文，不只保留摘要。
- `evidence`：任务所需原文、台词绑定、图片/音频/视频输入及其来源类型。素材文字描述不能代替必须检查的图片。
- `recent_decisions`：与本任务相关的已选方案、待解决歧义及失败尝试，不把整个思考过程或历史聊天当公共底座。
- `missing / available_context`：明确哪些信息未取、哪些必需输入缺失，以及可查询的对象/消息定位，不把“未载入”写成“不存在”。
- `actions`：当前有用的工具与其他任务能力的简短目录；显示集合和执行权限分开管理。

必要信息优先，预算不足先减少无关历史、重复叙述和可查询详情，不静默截掉用户要求、关键对白或来源。必需材料仍放不下时分解任务/分页取证，并显式说明缺口，而不是声称完整上下文已提供。预算依据实际 provider 上限、输出预留和媒体成本；没有真实 token 统计时标明是字符估算。

只读查询支持按 ID 获取镜头详情、明确范围的剧本/聊天原文、相关资产或操作回执，返回来源版本与截断标记。查询限于已授权项目与关联素材，不通过“找上下文”访问无关项目。初期采用已知引用、明确范围和可追踪原文定位，不引入向量数据库作为前提。

摘要是导航，不是新的事实权威；原始聊天和业务记录不被删除。过期摘要可以重建，但不能覆盖当前 ref 选择、显式对白绑定或用户最新修改。素材说明、历史工具返回等作为数据，不因进入工作包获得指令权限。

### 4.6 自主选任务，而非硬编码路由

已有确定任务的入口（例如写某个 Shot 的提示词、处理某次失败）直接构建对应工作包，不额外加一次路由模型调用。自由聊天从目标理解工作包开始，由当前 Agent 的正常决策选择后续任务，不建立按用户措辞匹配的任务分支表，也不新增专门的路由 Agent。

模型可提出“检查相关素材”“读取前一镜头”“切换到镜头修改”等请求；框架检查目标、权限和版本后刷新工作包。工具子集用于降低干扰，而非永久封锁其他合法能力；任务切换入口和能力目录必须可发现。错误选择工作包时能返回总览或取得缺少的上下文，不因为猜错任务类型而卡死。

切换仅改变视野，不产生业务写入，也不重置工具、重试或资源预算。一次成功查询的新证据可以支持新方案，但不能通过不断切任务清空失败记录。

如果“只修提示词”的恢复发现必须改台词，Agent 可以报告证据并请求改变范围，不能借切换任务直接修改台词。反过来，原授权已经允许创作调整时，不因任务名称改变就重复请求确认。

### 4.7 上下文与状态的一致性

工作包构建复用当前快照读取和 compare-and-save 能力；跨记录读取时检查相关版本，发现中途变化则重建，不能把混合版本当成一个有效快照。真正修改/提交时再次核对版本，模型看到的工作包不是永久有效的授权令牌。

补查的信息也加入依赖清单。用户中途换 ref，旧工作包不能继续激活旧输入的生成结果。任务切换携带已验证的来源与未决事项，而不是复制一份容易漂移的“新记忆”。

普通 prompt writer、尾帧 writer、Legacy 和 Harness 共享工作包构建契约，可以有不同写作策略与传输封装，不能维护互相矛盾的事实副本。

## 5. 版本、证据与依赖

### 5.1 区分修改冲突与产物失效

对象 revision 用来判断“我正在修改的对象是否已被别人更新”。依赖指纹用来判断“这个产物实际使用的内容是否变化”。二者不合并成一个项目级 hash。

提示词输入清单包含实际使用的镜头要求、对白绑定版本、图片内容哈希及 Picture 编号、音频绑定、适用的导演要求和生成契约版本。显示名等未使用字段变化不必让全部产物失效；实际进入生成输入的名称变化则必须计入。

视频绑定确切提示词产物、素材内容、生成参数和 pipeline 契约版本。尾帧绑定确切视频产物及提取参数，不绑定可变的“latest job”。共享 Library 同 ID 换文件也视为不同输入内容。

P1A 复用并记录现有输入签名，P1B 再以显式、可测试的依赖函数统一产物失效，不建设通用图数据库或任意 DSL。模型提出的依赖不能省略框架已知的实际输入；同时不因“项目有变化”就全部重建。

### 5.2 对白来源不是提示词附属品

来源证据与提示词分开保存，沿用当前对白来源校验。改运镜不删除台词证据；真正修改台词、归属或源场景才更新相关版本。涉及语义变化时允许有证据的复核，不在普通修改后重新猜一次说话人。

模型观察、用户明确要求、素材描述和执行回执保持不同来源类型。结构化模型意见不自动升级成用户确认或确定事实。

### 5.3 旧结果与激活

任务执行期间输入改变，完成结果仍作为旧输入产物保存。自动激活需要当前输入依赖匹配、选择 revision 未变化且操作拥有该范围的激活权限。

用户可以明确选择旧版视频作为保留版本，界面标明来源；这不应把它重新标成按最新要求生成。不要把自动保护变成禁止用户使用历史作品。

## 6. 统一命令协议

API、Dashboard、Legacy Agent、Harness Agent、Managed Run 调用相同应用服务。初期命令范围为修改规格、选择引用、请求提示词、请求视频、记录结果、选择产物和取消指定操作。

命令携带 `command_id`、目标、`expected_revision`、调用来源、有效授权引用和 payload。后端从会话/请求上下文验证授权，不能信任模型自报的来源和权限。

执行边界：校验请求与范围 → 加载权威状态 → 检查版本/幂等键 → 保存合法变更及回执 → 返回新版本、影响清单或结构化错误。推理和外部网络调用不能占用数据库事务或项目锁。

相同 command ID 与相同 payload 返回已有回执；相同 ID 携带不同 payload 返回冲突。用户明确要求“再拍一个版本”使用新的 command ID，即使输入相同也可以执行；内容哈希不能成为永久禁止再生成的理由。

长操作先保存输入快照与提交意图，再在事务外执行，完成后重新检查激活条件。参考文件必须通过已有内容校验并冻结输入或使用不可变内容副本，不能只校验一个随后可能被覆盖的文件路径。

业务拒绝返回明确 code、目标、预期/实际版本、证据及可行下一步，不把英文异常文本或关键词作为恢复协议。

## 7. 执行与恢复协议

### 7.1 区分几个维度，避免第二个万能状态

Operation 生命周期建议为 `queued / running / reconciling / succeeded / failed / cancelled`。等待 GPU、等待外部结果用 `wait_reason`；取消请求用 `cancel_requested_at`，不能提前声称外部任务已取消。

Managed Run 控制生命周期沿用简单的 `draft / active / paused / stopping / stopped / completed`。等待原因与生命周期分开：活动 run 可以等待资源或外部结果；需要用户选择时才进入有具体问题的暂停。

一次聊天回合结束不是 run 完成条件。Run 完成需要其当前目标内没有未解决工作；跳过的 shot 单独报告，不能包装成全部生成成功。

### 7.2 失败分类与行动边界

| 情况 | 框架行为 | LLM 的空间 |
| --- | --- | --- |
| 临时服务/网络错误 | 有界重试，记录尝试与退避 | 在预算与授权内选择其他可用策略 |
| 输入 revision 冲突 | 不覆盖，刷新事实 | 基于新事实重新提出动作 |
| 提交超时但可能已经执行 | 标为 reconciling，先查外部任务/回执 | 不得通过换工具盲目重复提交 |
| 缺少必需输入或权限 | 给出作用范围明确的问题 | 可自主补齐已授权材料，否则询问 |
| 有争议的语义或艺术判断 | 返回证据、置信边界与建议 | 选择修改、解释或提出不同创作方案 |
| 同输入、同失败、没有新信息 | 结束该无效尝试链，保留证据 | 可提出实质不同且合法的新方案，不无限换措辞重试 |

不承诺外部执行严格 exactly-once：没有 provider 幂等键或可查询记录时，丢失确认仍存在不确定窗口。必须显式报告未知，不能把未知当失败后自动重发。

### 7.3 取消与局部失效

`cancel_operation`、`skip_run_target`、`stop_run` 是不同命令。取消一个操作不自动取消其他 shot；依赖该结果的工作进入等待/重新规划，没有依赖的工作可在权限和资源允许时继续。

停止 run 撤销后续自动调度权限，并按 stop 的既有产品语义取消该 run 拥有的活动工作；不能取消手动创建或其他 run 的任务。晚到结果保存为历史，不恢复已停止的 run，也不自动激活。

计划依赖允许 LLM 更新，但在接受前检查合法对象、循环依赖、权限和版本。新增费用、扩大镜头范围或改写锁定内容不由“自主规划”隐式授权。

## 8. 持久化与迁移策略

P1A/P1B 保留现有 JSON 存储、单后端进程与已有恢复机制，只做上下文和业务边界收敛。明确不把阶段一称为已经具备跨文件事务或持久化幂等保障。

P2 持久化阶段推荐使用本地 SQLite 作为已迁移 Director 项目的业务状态事务存储；媒体留在文件系统。用途是原子提交规格/选择关系/操作回执/待处理事件，不是更换数据库就能自动获得可靠性。不引入 Redis、消息集群或全量 event sourcing；存储迁移不作为上下文试点的前置条件。

正式迁移必须满足：

1. 先统一 repository 接口和写入边界，再迁移数据；禁止绕过 repository 写新内核实体。
2. 按项目切换权威存储，不按同一字段同时双写两套权威；试验先用合成项目/明确允许的副本。
3. 切换前停止该项目的新写入，确认没有活动聊天、待提交或结果未知的操作，备份并记录输入校验值。
4. 导入后核对对象数量、引用完整性、当前选择和历史产物；校验通过才原子切换存储版本标记。
5. 旧 JSON 保留为只读备份/导出，不允许旧版本进程继续向已迁移项目写入。旧项目普通读取不触发迁移。
6. 现有 Job store 和生成 adapter 先保留。新事务记录中的 operation/reservation 是业务请求权威；JobRecord 是关联执行尝试。两者间断点由关联 ID 与恢复过程处理，不能伪装成跨 SQLite/JSON 的原子事务。
7. 结果记录与待处理事件在同一事务提交，事件消费支持去重与重复投递。运行时内存 task 不是唯一的待办依据。

回退边界：试运行未产生新写入时可切回原备份；产生新写入后不能简单切旧开关，否则会丢作品/回执。必须先停止调度、核对外部任务并导出兼容快照；无法无损映射时保留只读访问并前向修复。绝不把恢复备份等同于撤销已提交的外部生成。

## 9. 分阶段重构计划

每阶段有独立验收，完成一阶段不自动授权下一阶段。以下是路线和范围；首阶段的逐文件 TDD 实施清单在本设计确认后编写。

| 阶段 | 交付物与主要代码边界 | 退出条件 |
| --- | --- | --- |
| P0 基线与不变量 | 梳理写入口，以及 `chat_context.py`、`harness_runtime.py`、`chat_orchestrator.py`、`tool_schema.py` 的上下文组成；保存脱敏故障轨迹与实际输入清单 | 区分信息缺失、旧信息干扰、决策和执行错误；确认模型实际看到了什么，不只统计 prompt 长度 |
| P1A 任务上下文试点 | 单 Shot 提示词工作包、公共底座、带版本的补查接口与能力切换；正常/尾帧 writer 共用证据；Legacy/Harness 适配；只读对比后切换测试路径 | 必需证据不丢、无关信息可省、缺失可发现可补查；保持旧版授权和 stale 检查；是否提高质量有对照结果 |
| P1B 单 Shot 执行闭环 | 新增内聚的规格变更/依赖/状态投影模块；统一 API、两种 Agent、手动/托管提交入口；继续调用现有 prompt writer、Job runner 和存储 | 修改 Shot → 提示词更新 → 视频提交 → 结果到达使用一致规则；没有旁路；旧结果不能覆盖新要求 |
| P2 持久化操作 | repository 事务适配、不可变输入清单、操作回执、待处理事件和重启 reconciliation；项目级试验迁移 | 故障注入覆盖提交前后、回执落盘前后、结果落盘前后；不盲目重发，不丢已完成结果 |
| P3 托管与尾帧 | Managed Run 使用统一操作与投影；尾帧绑定确切视频版本；计划可在权限范围内调整；取消与等待作用域明确 | 取消一个 shot 不误取消全片；重启可恢复已授权待办；一次模型回合结束不等于流程失败 |
| P4 工作包推广与兼容收尾 | 将已验证的契约推广到规划/素材/恢复等已有任务；前端状态组件与 API types 消费统一投影；删除已无消费者的重复规则；更新架构文档 | 每类工作包独立通过充分性与质量对照；保存后 shot/run 视图一致；摘要接口不装载全量媒体；无旧写入者后才删旧字段 |

顺序为 P0 → P1A → P1B → P2 → P3 → P4。P1A 可独立验收，不依赖数据库迁移；如果上下文收益不成立，先调整信息选择，不因此否定或强推整个状态重构。P1B 即提供最小兼容视图并验证 UI，不等 P4 才发现接口不兼容。P4 不另起一轮视觉重做。

### P1A 的交付边界与落点

- 基于现有 `chat_context.py` 抽出可测试的公共事实读取与工作包构建；在 `agents/director/` 新增任务契约、工作包构建、上下文查询三个内聚模块。初期只实现总览和单 Shot 提示词包，不为六类任务各建一个独立 Agent。
- `harness_runtime.py` 和 `chat_orchestrator.py` 使用同一构建器；`tool_schema.py` / `stage_guides.py` 提供任务相关指南和可发现的能力目录。它们不另写领域事实，不更换现有运行时。
- `service.py`、`dialogue_preflight.py`、`tail_prompt_review.py` 消费同一份目标规格、来源与素材清单。保留旧写作策略，先验证上下文差异而非同时更换提示词写法。
- 新增工作包充分性、跨任务补查、输入过期、授权保持、双运行时一致性测试；保留原始聊天和现有上下文路径作为明确的试点回退选项。
- 试点先离线构建新旧工作包并比较，不同时执行两套写命令或提交两次视频；真正 A/B 使用隔离 fixture 或明确允许的测试副本。回退只改变上下文构建器，不撤销已经发生的业务操作，不绕过校验。
- 第一阶段不新增数据库、外部服务、成片 QC、自动重拍、模型角色池或关键词路由规则。具体文件名、接口和 TDD 步骤在书面设计确认后的首批实施清单固定。

### P1B 的明确边界

- 先统一现有 Director 单 Shot 的变更与生成边界，不迁移所有项目，不切数据库，不重写 Harness/GPU/provider。
- 正常提示词和尾帧提示词可继续有不同创作策略，但读取同一套规格与证据、提交同一种产物结果。P1A/P1B 不改托管的多 Shot 调度策略。
- 新模块优先放在 `backend/app/core/projects/` 的规格、依赖和视图边界；应用命令放在独立的 application service，不能继续堆入 `DirectorService`。具体文件粒度由下一份实施计划给出。
- API 与 tool handler 只适配参数、调用应用服务、返回结果；不能在 handler 再实现一遍清理/失效规则。
- 保持 H3 六段输出、现有角色/对白协议和用户创作授权语义。MV、JSON Production、无 Shot 的独立生成保留旧语义并做兼容测试，不被隐式纳入新 Director 规则。

## 10. 测试与验收

### 10.1 必须通过的确定性轨迹

| 轨迹 | 必须证明的结果 |
| --- | --- |
| 台词恢复 → 改镜头 → 再写提示词 | 来源与说话人不因清理派生提示词丢失；普通运镜修改不重新提取归属 |
| 同 ID ref 内容替换 / Picture 重排 | 对应输入签名变化；旧提示词不被静默复用；不误伤无关 shot |
| 推理或视频生成中用户修改输入 | 保存/激活有版本检查；旧结果保留但不冒充新版 |
| UI 修改与 Agent 修改等价字段 | 同样的规格、失效关系和视图，不因入口不同而分叉 |
| 重复命令与明确“再拍一版” | 前者复用回执；后者允许新的 operation，不被内容去重误拦 |
| 提交确认丢失、结果重复送达、后端重启 | 已提交先查询；结果消费幂等；不盲目创建第二个外部任务 |
| 取消单个操作 / 跳过目标 / 停止 run | 三种作用域不同；无关任务不受误伤；停止后晚到事件不复活 run |
| 新旧尾帧切换、源视频切换 | 同一衔接选择唯一；历史可追踪；下游依赖指向确切源版本 |
| 素材不变的多种镜头/表演方案 | 不要求唯一黄金提示词；合法创作变体都能通过 |
| API 读取、旧项目导入、存储回退 | 读取不写生产数据；导入可核对；回退不丢新增状态或误重发任务 |
| 加入大量无关镜头/历史记录 | 单 Shot 工作包不随无关内容线性膨胀；必要项目要求不被挤掉；缺少详情有明确查询入口 |
| 前一镜头动作/全局导演要求影响当前 Shot | 依赖连续性和有效要求进入工作包；不是只按当前 Shot ID 机械切片 |
| 原文未载入、摘要过期、同名或歧义目标 | 明确缺口并返回有版本的原始材料；不把摘要当权威，不静默猜目标 |
| 工作包选择错误 → 补查 → 切换任务 | 能纠正视野，预算不重置，授权不扩大，已有失败与决定不丢 |
| 补查期间 UI 换 ref / 修改台词 | 检测到版本变化，旧任务不能保存或激活过期结果 |
| 相同任务进入 Legacy / Harness / writer | 必需事实与授权相同；封装可不同，不能因传输路径漏来源 |

优先复用并扩展现有 `test_dialogue_camera_revision.py`、`test_scoped_prompt_retry.py`、`test_job_recovery.py`、`test_job_shot_sync.py`、`test_managed_run_continuation.py`、`test_harness_runtime.py` 等测试。新增轨迹用 fake provider/外部任务实现确定性故障注入，不能只测孤立函数。

### 10.2 语义与创造力评估

真实模型验证是独立、显式授权的测试，不因为本计划存在就重拍用户影片。用固定样本集、相同模型与推理设置比较重构前后：任务完成、自动恢复、人工介入、错误放行、合理创作误拦、重复执行、延迟与调用消耗；同时统计关键信息遗漏、补查成功/次数、错误任务切换与实际输入长度。报告样本数与多次运行的差异，不把一次成功当总体改善。

P1A 的推广门槛：全部确定性充分性/权限/版本测试通过；对照中没有已确认的新增关键遗漏、未授权修改或错误提交；语义质量不能只用 token 减少来替代。若真实模型样本显示质量下降，保留旧路径并修正工作包选择后再评估；如果尚未做真实模型对照，只报告机制测试通过，不声称质量提高，也不默认全量切换。

同时测试应当拒绝的违规与应当允许的变体。改变角色名、语言和场景后问题仍应可处理；不能把 Titanic/Kira 案例做成生产关键词条件。首次实测建立基线，再设置有依据的改善目标，不提前捏造错误率或性能收益。

## 11. 可观测性与教学交付

每条操作记录至少可追溯 project/shot、command/operation、输入 revision、artifact、provider task、错误分类与恢复尝试。模型调用另外记录工作包种类/版本、载入的来源 ID、省略项、补查轨迹和输入长度，不默认把用户剧本/图片全文重复写进诊断日志。用户看到的是具体等待原因和必要操作，不是一长串原始英文异常。

每阶段报告用同一结构：实际失败 → 信息在哪个边界丢失 → 采用的传统工程机制 → 仍由 LLM 决定什么 → 通过/失败证据 → 剩余限制。不单独建设一套复杂的“教学 Agent”。

对照关系：规格版本≈乐观锁；产物依赖≈增量构建；命令回执≈幂等业务接口；待处理事件≈事务 outbox；恢复≈外部状态对账。它们解决确定性执行问题，不会消除 LLM 或视频模型的语义不确定性。

## 12. 非目标与风险控制

- 不加入新 Agent 层、通用流程 DSL 或额外 judge 模型作为默认方案。
- 不强制所有镜头顺序衔接，不要求每个正常创作决定人工确认。
- 不把艺术偏好或单次模型审核意见升级成永久硬约束。
- 不声称此次框架重构能保证生成视频的服装、口型和表演百分之百正确。
- 不顺带更换模型服务、重启服务、改影片内容或优化整套前端。
- 最大风险是迁移期间双权威与漏掉写入口；用项目级切换、入口契约测试和禁止旁路写入控制。
- 第二个风险是过度失效/过度阻断；用细粒度依赖、可解释差异以及“应当允许”的反例测试控制。
- 第三个风险是扩大范围；先交付 P1A 的任务上下文试点，再做 P1B 的执行闭环，独立设计和验收持久化与托管阶段。
- 第四个风险是上下文裁剪损害叙事连贯或增加查询成本；用必要信息清单、来源可追溯、跨镜头反例和同条件质量对照控制，不以输入越短越好为目标。
