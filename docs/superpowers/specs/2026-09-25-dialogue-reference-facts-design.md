# Director 对白与参考事实校验设计

状态：设计草案，等待书面方案确认；尚未进入实现。

## 0. 最高原则：加强执行框架，不把导演判断写死

用户补充：目标是降低 agentic system 的错误率，同时保留 LLM 的创意性；任何基于内容关键词的硬编码都必须重新审视通用性。用户有传统产品软件工程背景，希望在本项目实践中理解构建 Agent 系统的思维。

将职责明确分成三类：

| 类别 | 框架职责 | LLM 的自主空间 |
| --- | --- | --- |
| 执行不变量 | 权限、资源预算、合法 ID、版本一致、幂等提交、不能覆盖用户新修改 | 在合法工具和当前授权范围内选择行动 |
| 有来源的任务约定 | 保存谁提出、适用范围、版本、是否允许改编，避免遗忘或偷偷漂移 | 在已授权范围内修改方案并形成新版本，不必为每个导演选择询问用户 |
| 创作与语义判断 | 提供完整上下文、反馈证据和可恢复工具，不指定唯一正确答案 | 运镜、表演、节奏、构图、参考组合、镜头衔接和合理的创作变体 |

不把所有剧本描述、资产备注或模型观察都提升成永久硬约束。已确认裙装是这一次角色设定的数据，不是程序中的 `if name == Mia` 或裙装词表。模型观察永远可能出错；结构化只让错误可定位，不会自动让观察成为真相。

协议标记和 schema 的严格检查与内容关键词判断不同：检查 `<Picture N>` 指向已连接输入是工具协议约束；看到 `pantsuit` 就拒绝则是脆弱的业务语义规则。产品逻辑不能根据 Titanic、角色名、场景名、服装词或英文报错文案分支；这些具体值仅用于测试样本。

创作授权和执行快照也不同：允许 Agent 改编的阶段可以修改对白或归属，并记录新的创作版本；执行阶段必须忠实使用该版本，不能在提示词转换时无意换人。当前任务是继续拍摄已选分镜，不能把“保持创意性”解释为自动授权改写这些分镜；后续用户要求改编时可以更新约定，不把保护机制变成永久封锁。

语义审核默认产生带证据的建议或修复请求，不因单次模型意见就否定创作。只有明确违反执行不变量、当前不可修改的用户要求，或缺少完成动作所必需的信息，才阻断对应动作。局部不确定性不能无条件升级为整个项目停机。

## 1. 目标与范围

用户要的是 Agent 在实际制作中自己处理错误，而不是由人手动修 Titanic 的单个镜头。第一阶段先把两类可在生成前发现的错误拦住并自动修复：对白说话人错配，以及已确认的参考事实被模型重新解释错。

本阶段覆盖 Director 模式下绑定 Shot 的原生 Agent、Harness Agent、手动提交与托管提交入口。它们共享同一份校验结果，不能通过换入口绕过。MV 的精确源音频、JSON Production、无 Shot 的独立 H3 请求保持原有语义，不顺带迁移；共享校验器新增参数保持向后兼容。

不包含成片视觉 QC、自动重拍、角色去重模型、新一轮 UI 重做或服务重启。不会修改现有剧本、已完成 Shot 或视频，不批量重跑。摄影、调度和哪些镜头衔接仍由 Agent 按需求判断。

## 2. 真实问题与当前代码

- Titanic Shot 8 的提示词把 “Porridge…” 从 Tao 分配给 Mia，把 “That's a lot of food.” 从 Mia 分配给 Male Passenger，把 “Fair point.” 从 Tao 分配给 Mia。现有校验器接受这些提示词，因为文字和顺序都正确。
- `Shot.dialogue` 是 `list[str]`，当前数据没有逐句角色信息；`_validate_dialogue` 比较的是 spoken words，无法验证说话人。
- Shot 10 的视觉描述同时出现 `pantsuit` 和 `knee-length pencil skirt`，提示词只保留了 `pantsuit`。实际图片仍是米色裙装，资产的 approved notes/description 为空。
- Shot 8 出现重复 Mia，但这属于后续生成质量问题。本阶段不能声称解决重复人物、口型或实际声音归属。

现有安全能力继续保留：真实图片内容签名、提示词失败草稿隔离、输入变化检查、托管事件去重，以及旧新尾帧不能同时激活。

## 3. 方案选择

| 方案 | 收益 | 局限 |
| --- | --- | --- |
| 只强化提示词 | 改动小 | 说话人仍会在自由文本中丢失，无法形成可测试的边界 |
| 每次增加一个通用 LLM 审核 | 能发现部分语义错误 | 增加延迟和误报，仍可能与写作模型犯同一种错误 |
| 有来源的结构化事实 + 确定性编译/校验 + 有限语义复核 | 可以复现、缓存、解释和精确修复 | 需要兼容旧数据和维护版本签名 |

采用第三种。事实是否有来源、ID 是否匹配、缓存是否过期由代码判断；难以用规则判断的图像语义允许模型复核，但模型不能自行冒充用户确认。

## 4. 对白数据与旧项目兼容

增加可选的 `dialogue_lines`，每项包括稳定 `line_id`、`speaker_id`、显示名、原始 `text`、语言，以及来源记录。来源记录包含来源类型、脚本版本、场景/原文定位和可复核的原文引用，并继承当前任务对原文、归属、顺序的修改权限。角色 ID 属于项目叙事身份，不等于 actor 资产 ID：同一人的全身图和脸图不能被当成两个角色，画外音也不要求有可见演员图。

保留现有 `dialogue` 字段作为 UI/API 兼容投影。两种字段同时提交时必须逐句一致，否则返回具体冲突，不能静默选一边。只修改旧 `dialogue` 时，后端立即使旧的说话人映射和派生提示词失效。

旧项目读取时不写回、不批量迁移。第一次为某个未完成或明确要求重新生成的 Shot 写提示词时：

1. 优先使用有效的显式逐句角色绑定。
2. 否则从当前剧本中提取带说话人的段落，以该 Shot 的场景、连续台词与原文引用定位。
3. 模型可提出匹配，但代码必须核验引用、版本和台词覆盖。重复台词按出现位置区分，不仅以文字做 ID。
4. 唯一且有证据的匹配可自动持久化；真实歧义只针对该句提出一个具体问题，不能靠“当前谁有声音素材”猜说话人。

无对白镜头不要求说话人映射。缺少某人的 Voice 参考本身不等于不能生成，也不能把其台词转交给有 Voice 的角色。

## 5. 保留对白归属，不规定唯一创作表达

最终送往 H3 的格式仍是现有六个非空字符串字段，不改 Ref2AV 接口。

内部草稿保留每次对白使用与 `line_id`、`speaker_id` 的结构化关联，原文、归属和次序依据本次有效任务约定检查。未知 ID、未授权换人或漏句进入现有修复路径；经过授权的改编产生新版本后可以合法通过，不能把它判成错误。

撤销“所有创作必须使用固定 `<speech .../>` 占位模板”的先验要求。H3 适配层可以为已锁定的对白生成最小必要的角色/语言/`<d>` 标记，但不生成固定表演句式、不限定一种段落布局，也不决定每句的镜头、动作、语气和时机。实施计划必须用当前 writer 的最小接口扩展保留关联，并验证其确实改善错配；不以建立复杂的全新提示词编译语言作为前提。

内部草稿和最终编译结果分开保存。已有旧提示词可以显示和播放，但未通过新版本校验的提示词不能在下一次 Director 生成时被静默复用。人工编辑的提示词也必须重新匹配逐句角色和文本；能无歧义恢复绑定则自动编译，不能恢复则标记需修订，不能视为人工编辑即可绕过。

代码可以保证结构化绑定引用正确的记录和版本，但仅有正确元数据不能证明自由文本与成片也正确。动作 prose 若明确与本次对白绑定冲突，进入有证据的语义修复；不以邻近关键词猜说话人，也不把审核模型的结论当确定性证明。当前执行约定下，原对白中的省略号、原语言和重复词保持不变；本阶段不自动改写剧本标点，未来明确授权的改编不受永久禁止。

## 6. 参考事实：来源、版本和作用范围

在项目的 `agent/reference_facts.json` 中原子保存引用级事实，不默认改写跨项目共用的 Library 资产。每条事实绑定 `asset_id`、`file_key`、图片内容 SHA-256、叙事角色/对象、属性、值、来源与版本。

区分三类信息：

- 用户明确确认的事实：带可验证的用户请求或已确认项目选择的引用。
- Library 已保存的描述/备注：保留原文和字段来源，不把资产名称当图片证据。
- 视觉观察：保留模型、图片签名和观察证据，始终标为模型观察，不能自动升级为用户确认。

既有明确确认可自动导入，但必须能定位到当前记录中的真实来源，并与当前图片版本关联；不从聊天摘要或模型声称“用户已经同意”推断确认。旧项目没有已确认事实也能正常工作，以视觉观察作为未确认依据，无需给每张图片补一轮人工审批。

优先采用仍有效且适用于当前任务的最新显式用户选择。若用户意图与真实图片矛盾，不能通过改写图片描述来掩盖冲突；先重查图片，仍矛盾且该属性是本镜头必要的不可修改要求时说明具体属性和版本并询问。可在已授权范围内解决的差异由 Agent 自行处理并记录理由。旧剧本服装不得推翻后来明确批准的新 ref，但用户之后授权的新创作版本可以替换旧选择。

## 7. 观察冲突如何自行处理

观察阶段把关键身份、服装、道具事实与自由描述分开。每项事实附证据短句；不能从近景推断看不到的下装。多视图 sheet 应标记为一个角色的多个视角。

出现“裤装由铅笔裙组成”等内部冲突，或与已确认事实矛盾时：

1. 不让矛盾描述直接进入 H3 写作输入。
2. 对相关图片进行一次有针对性的复查，传入具体争议属性；不重看所有无关资产。
3. 复查能根据像素消除歧义时，保存新观察并废弃错误派生描述，无需用户介入。
4. 仍不确定且不影响本镜头的属性，省略未经证实的描述并记录不确定性；关键身份/服装确有冲突时只问必要的问题，不要求用户重做整个 storyboard。

H3 写作使用区分已确认事实、观察和未决事项的快照，明确绑定每张 Picture 的实际编号和职责；不会为了等所有非关键细节“完全确定”而阻断写作。最终候选中若出现与当前不可修改要求有证据冲突的属性，修复相关段落，而不是改参考图来迎合错误提示词。语义判断不能变成一组把所有“裙装/裤装”词全局禁用的规则，也不能承诺确定性检测任意视觉错误。

## 8. 缓存、并发和执行入口

新增执行前快照签名，包含：契约版本、脚本/导演要求版本、逐句绑定、图片字节、事实来源版本、实际 Picture/Audio 顺序和当前 Shot 输入。其版本必须参与视觉观察缓存、material review、提示词草稿修复键和提交检查。

区分两种变化：

- 用户修改台词、说话人、参考或确认事实：使相关执行前快照失效，按现有 authored-input 规则处理托管计划的陈旧状态。
- Agent 对同一份未变输入补齐有来源的派生记录：由当前事件持有者原子写入，不把正常的契约补齐误判为外部编辑而卡住托管。

写提示词前和真正提交 H3 前都重新比对快照。旧的并发请求不能覆盖新引用或新绑定。换图即使 asset ID 没变，图片 SHA-256 改变也必须失效；换文件顺序则重建 Picture 绑定，不把语义角色 ID 跟着位置换掉。

所有绑定 Director Shot 的提交入口调用同一 preflight。已完成视频及其当时的输入快照保持不变；新约束只影响下一次明确请求的生成，不把历史成片自动标失败或重拍。

## 9. 有限修复与可见反馈

继续使用现有失败草稿隔离和托管重试预算，不增加互相嵌套的无界重试。初始默认视觉争议最多额外复查一次，提示词修复消耗现有一次恢复机会；预算集中在执行策略中，不散落为针对人物、场景或词汇的特殊规则。没有新证据或输入变化时不重复相同调用。预算限制资源消耗，不替 Agent 指定修复内容。

错误返回结构化问题项：错误码、Shot/line/asset ID、期望事实、实际冲突、证据和可执行建议。系统展示简短原因，例如“第 2 句应由 Tao 说，正在修复说话人绑定”。本阶段只在现有状态/错误区域补充信息，不新增永久占空间的面板。

只针对当前 Shot 暂停或修复，不修改其他 Shot、不扩大取消范围。遇到缺失文件、不可解歧义或真实用户选择冲突，保留候选与证据，不反复猜测。

## 10. 验收与回归样本

| 测试 | 必须满足 |
| --- | --- |
| Shot 8 三句错误角色绑定 | 生成前发现并自动编译为剧本中的 Tao、Mia、Tao；不能因台词文字齐全而放行 |
| 重复台词、同名角色、画外音 | 按句实例和来源定位；没有证据时不猜角色，不依赖 Voice 数量 |
| 老项目仅有 dialogue 字符串 | 可读取，唯一剧本匹配可自动补齐；读取不修改已完成 Shot |
| Dashboard/Agent 修改对白 | 旧映射、草稿与提示词签名失效；不保留错位 line ID |
| Shot 10 裤装/铅笔裙矛盾 | 原矛盾不进入提示词；复查可解决，不需要用户再次确认已确认的新 ref |
| 近景看不到下装 | 不把“未知”写成裤装，不把看不到当作与裙装冲突 |
| 同 ID 替换图片、调整 Picture 顺序 | 前者失效旧事实版本，后者更新编号且保留语义角色 |
| 推理中用户换 ref 或改说话人 | 旧请求不能保存/提交过期结果，也不能触发无关 Shot 取消 |
| 原生/Harness/手动/托管入口 | 同一输入得到同一契约约束，不能绕过 |
| MV、JSON Production、无 Shot 独立 H3 | 原有行为不变；不误用 Director 的对白绑定 |
| 更换角色名、语言、服装和场景 | 同类信息丢失/矛盾仍可处理，不能依靠 Titanic 专用关键词 |
| 用户批准裤装或授权重分配对白 | 新的有效创作版本正常通过；旧失败样本中的词不成为禁词 |
| 相同约定下不同运镜、节奏、表演 | 多种合格输出通过，不要求复刻一条黄金提示词 |
| 审核模型无证据反对正常构图 | 不升级为硬失败；区分建议、未决问题和已证实违约 |

测试使用从真实失败抽取的最小文本 fixture 和合成图片，不把生产视频/私人项目全量数据提交进测试库。先验证失败测试能重现旧问题，再通过单元、API、前端兼容测试；真实模型验证放在后续用户授权的测试项目或明确选中的镜头中，不重跑当前已完成 Titanic 镜头。

必须同时测试应该拒绝的错误与应该允许的创作变体。确定性边界使用单元/集成测试；语义部分用多案例、重复运行的评估，记录错误放行、正确创作被误拦、人工介入、恢复成功率、延迟和成本。由用户对创作质量/多样性做抽样判断，不能仅用单一模型评分证明创意被保留。减少系统报错不等于减少实际错误；让任务停得更多也不等于系统更可靠。

## 11. 实施边界与顺序

后续实现计划按两个可分别验收的子阶段展开：先对白契约，再参考事实契约。每阶段覆盖数据读写、Agent 工具、所有目标提交入口、缓存失效与回归测试后再进入下一阶段。

逻辑拆到独立的对白契约、参考事实及 preflight 模块，由现有 `service.py` 编排；不继续把解析、缓存、修复细节全部堆入 service。具体文件和步骤在书面设计获批后形成实施计划。

成片 QC 和自动重拍仍是后续独立设计：即使本设计实现通过，也不能宣称已经解决重复 Mia、实际声音归属或所有服装漂移。

## 12. 设计审阅结论

已检查兼容投影冲突、匿名/画外角色、来源伪确认、不可见服装、图片同 ID 换内容、托管派生状态写入及多入口绕过风险。生产状态不迁移，现有未提交实现不纳入本设计提交。

## 13. 实践中的教学方式

每项改进配一段简短的决策说明，不单独制造庞大的教学流程：

1. 实际失败与可复现证据，不把一个片段的结果当总体错误率。
2. 失败发生在意图表示、上下文/记忆、推理决策、工具执行还是结果评估；先找信息在哪个边界丢失。
3. 与传统工程的对应：schema/类型、数据来源、缓存失效、事务/乐观锁、幂等性、状态机、可观测性；说明哪些判断仍然具有不确定性。
4. 至少比较最小的框架修复与简单提示词修改，解释为什么选前者或后者；不预设每次都需要新 Agent、新审核器或新 schema。
5. 用反例检验泛化及创意自由，展示改进前后的收益、误报和成本，而不只展示测试数量。
